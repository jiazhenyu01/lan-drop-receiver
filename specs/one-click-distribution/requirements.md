# 局域网投送站一键分发需求

状态：待用户确认  
范围版本：0.1

## 1. 结论与约束

Chrome 扩展不能在安装或卸载时直接执行 macOS 脚本，也不能自行写入
Native Messaging Host 的系统注册目录。Chrome 提供的卸载回调只能打开
HTTP/HTTPS 页面，不能用于本机清理。

因此，可交付产品应是一个整体套件，而不是单独的扩展文件：

1. Chrome 扩展负责交互、二维码和会话控制。
2. macOS 本机助手负责局域网服务与文件接收。
3. 安装器负责安装本机助手、注册 Native Host，并引导 Chrome 安装扩展。
4. 完整卸载器负责移除扩展和所有产品自有的本机内容。

在非企业 Chrome 环境中，扩展启用仍必须经过用户确认。正式对外分发时，
扩展应发布到 Chrome Web Store；macOS 安装器应进行 Developer ID 签名和
Apple 公证，才能避免其他电脑上的安全警告。

## 2. 产品目标

面向普通 macOS 用户提供可分享的安装包。用户不需要安装 Node.js、进入终端、
打开开发者模式或手动配置 Native Messaging Host，即可完成安装、使用和卸载。

## 3. “无残留”的定义

完整卸载后不得保留以下产品自有运行内容：

- 本机助手及其资源文件；
- Native Messaging Host 注册文件；
- 安装回执和产品配置；
- 安装器创建的 Chrome 外部扩展注册文件；
- 正在运行的本机助手进程；
- 未完成上传产生的 `.lan-drop-*.part` 分片；
- 扩展自身由 Chrome 管理的存储状态。

接收成功的图片和文件视为用户数据，不应在默认卸载中静默删除。完整卸载界面
应提供“同时删除已接收文件”的明确选项。

Chrome 自身的通用日志、缓存、浏览器历史，以及 macOS 的通用安装日志不属于
产品可安全定向删除的内容。卸载器不得为了追求字面上的“零字节残留”修改整个
Chrome Profile 或系统日志。

## 4. 用户故事

### 4.1 安装者

作为接收文件的用户，我希望双击一个安装入口即可安装全部必要组件，并在 Chrome
中完成一次明确授权后立即使用。

### 4.2 卸载者

作为不再使用产品的用户，我希望在插件内点击“完整卸载”，或双击独立卸载器，
即可删除所有产品自有运行内容，并得到清理结果。

### 4.3 分享者

作为分发者，我希望把同一个发行包分享给 Intel 和 Apple Silicon Mac 用户，
而不要求对方配置开发环境。

## 5. 验收要求

### R1. 一键安装

1. 当用户启动安装器时，安装器应展示将要写入的组件和路径。
2. 当用户确认安装时，系统应安装不依赖外部 Node.js 的本机助手。
3. 当安装完成时，系统应注册正确的 Native Messaging Host，并验证其可启动。
4. 当 Chrome Web Store 版本可用时，安装器应打开对应商店页面或写入受支持的
   外部扩展注册，并由 Chrome 展示启用确认。
5. 当安装失败时，安装器应回滚本次新增内容，不留下半安装状态。

### R2. 首次运行自检

1. 当扩展首次打开时，扩展应检查本机助手是否已安装及版本是否兼容。
2. 当本机助手缺失或版本不兼容时，扩展应显示明确修复入口，而不是只显示
   Native Host 连接错误。
3. 当全部组件正常时，用户应可直接开启接收，无需额外配置。

### R3. 插件内完整卸载

1. 当用户点击“完整卸载”时，扩展应展示清理清单并要求确认。
2. 当用户确认时，扩展应请求本机助手安排安全的自清理任务。
3. 当本机清理任务已确认接管后，扩展应调用 Chrome 的自卸载能力。
4. 当清理完成时，产品自有运行文件、注册文件、未完成分片和进程应全部消失。
5. 当用户选择“同时删除已接收文件”时，卸载器才可删除接收目录中的完整文件。

### R4. 独立卸载兜底

1. 当扩展已被用户从 `chrome://extensions` 直接移除时，用户仍应能通过发行包内
   的独立卸载器清除本机助手。
2. 当本机助手损坏或无法连接时，独立卸载器仍应可以完成清理。
3. 当目标路径不符合预期时，卸载器应停止并拒绝扩大删除范围。

### R5. 残留审计

1. 当卸载完成时，卸载器应自动执行只读审计并展示结果。
2. 当发现产品自有残留时，卸载过程应返回失败并列出确切路径。
3. 当只剩用户选择保留的已接收文件时，审计应将其标记为“用户数据已保留”，
   而不是产品残留。

### R6. 通用发行包

1. 当发行包用于其他 Mac 时，应同时支持 Apple Silicon 与 Intel 架构。
2. 当目标电脑未安装 Node.js 时，安装和使用仍应成功。
3. 当用户没有开发者模式时，正式发行版仍应可安装。
4. 当发行版对外分享时，应包含版本号、校验值、隐私说明、安装说明和卸载入口。

### R7. 安全与隐私

1. 安装器不得创建 LaunchAgent、登录项或不必要的常驻服务。
2. 本机助手应只在用户开启接收时运行，并在会话关闭后退出。
3. 安装和卸载不得修改无关 Chrome Profile 数据或用户文件。
4. 扩展与本机助手应继续使用固定且可验证的扩展 ID 授权。

### R8. 更新兼容

1. 当扩展和本机助手版本不匹配时，界面应提示更新而不是继续运行不兼容协议。
2. 当覆盖安装新版本时，安装器应原子替换本机助手并保留安全的用户数据。
3. 当安装失败时，上一可用版本应继续可用或被完整恢复。

### R9. 测试

1. 发行前应自动验证安装、覆盖安装、插件内卸载、独立卸载和残留审计。
2. 发行前应分别验证 Apple Silicon 与 Intel Mac。
3. 发行前应验证 Chrome 新配置、已有配置、未安装 Node.js和本机助手损坏等场景。

## 6. 非目标

- 绕过 Chrome 的扩展安装或启用确认；
- 直接修改 Chrome 内部 Profile 数据库以强行安装或删除扩展；
- 为自动侦测扩展卸载而新增常驻监控进程；
- 默认删除接收成功的用户文件；
- 在未获得证书时声称安装包已签名或已通过 Apple 公证。

## 7. 待确认决策

1. 分发级别：
   - 推荐：Chrome Web Store（可设为不公开）+ 已签名、公证的 macOS 安装器；
   - 过渡版：未签名的内部测试包，会有 Gatekeeper 和 Chrome 手动确认步骤。
2. 平台范围：
   - 推荐第一阶段只支持 macOS，同时覆盖 Apple Silicon 与 Intel；
   - 如果需要 Windows，还需增加独立的 Windows Native Host、注册表安装器和测试。
3. 用户文件：
   - 推荐默认保留已接收文件，卸载时提供显式勾选彻底删除；
   - 也可以把“彻底删除已接收文件”设为默认，但存在误删用户文件风险。
